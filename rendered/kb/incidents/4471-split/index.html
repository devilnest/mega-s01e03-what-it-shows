Problem A · shared parser reads month first

The shared parser assumes month/day order while day-first tenants write day/month. A date such as 07/04 can become 4 July instead of 7 April. This cause covers app and email reports and form reports whose tenant does not use the month-first booking-v3 hint. It spans both booking-form versions; a version alone is not the grouping rule.

For example, R-41200 is an app report from harbour.dental (en-GB, booking-v2): a 7 April reminder became 4 July. R-41201 corrects the direction in the reporter’s account; it is a different report ID, not an export duplicate. Preserve that correction and verify against actual booking values when reproducing.

Engineering now reports the parser fixed: fix(dates): parse dd/mm for eu locales. Close this cause as completed. Regression criteria are ambiguous and unambiguous dates across supported tenant locales and channels, with the stored booking, reminder and invite checked together. These are verification criteria, not tests run by this review. A parser change alone does not repair the form’s misleading hint.

Problem B · booking-v3 tells day-first users to type month first

The booking-v3 hint prints MM/DD/YYYY for day-first tenants, while that form interprets input in the tenant’s day-first order. Following the hint therefore swaps month and day. This is a separate form contract failure, not another browser label for Problem A.

The affected form reports belong to alder.physio (de-DE), copper.studio (es-ES), and pale.harbour (pt-PT). R-41230 is copper.studio via form, tagged parser at intake but classified hint by the tenant and channel. R-41241 is alder.physio via form with browser locale en-US: the tenant remains de-DE. R-41251 is pale.harbour via form, also tagged parser. These examples show why the browser cannot decide the cause.

Engineering chose won’t fix because the booking-v3 form was retired. Close this cause as not planned, not completed: no hint patch is claimed. If that form or date-entry flow returns, align its hint, validation, parser and confirmation with the tenant’s locale and test users following the displayed hint. Keep that future verification separate from the parser fix.

Replace subject-only merging with cause review

Decision 0001 and the triage guide were last reviewed on 2024-06-11. The shared layout marks them stale after the configured half-year threshold. Accepted decisions are immutable: retain 0001 as history and propose a new decision rather than silently rewriting it.

Proposed replacement: resolve the tenant; inspect locale, form version, channel and symptoms; merge only when the cause matches. A subject is a search hint. Matching subjects can hide different causes, and different subjects can describe the same cause. Unknown tenants or inconsistent evidence stay unplaced for review; do not automatically merge them.
